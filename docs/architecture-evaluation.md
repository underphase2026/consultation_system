# [리포트] 언더페이즈 상담 및 견적 시스템 아키텍처 심층 분석 및 평가

**작성자:** Chief Software Architect
**대상:** 언더페이즈(Underphase) 통합 유무선 상담 및 견적 시스템

---

## 1. 전체 아키텍처 요약 (Architecture Overview)

**[계층형 아키텍처 및 모듈 분리 상태]**
현재 시스템은 NestJS의 철학에 맞게 Controller(HTTP 라우팅 및 인터페이스), Service(비즈니스 로직), Repository(데이터 접근) 계층으로 명확하게 분리되어 있습니다. 
특히 돋보이는 부분은 **도메인 격리(Domain Isolation)**입니다. 설계 초기 요구사항을 철저히 반영하여 기존 고객 관리(CRM) 도메인과 소스 코드 레벨 및 런타임에서 강하게 결합되지 않는 독자적인 `ConsultationsModule`을 구축했습니다. 이를 통해 CRM 로직의 변경이나 확장이 상담/견적 시스템에 어떠한 사이드 이펙트도 발생시키지 않으며, 추후 마이크로서비스(MSA)로의 분리가 필요할 때도 `ConsultationsModule`만 떼어내어 즉시 격리 배포할 수 있는 높은 응집도(Cohesion)를 확보했습니다.

## 2. 데이터베이스 및 엔티티 설계 분석 (DB & Entity Analysis)

**[스냅샷 데이터를 포함한 제약 조건 및 무결성(Data Integrity)]**
크롤링 기반의 통신사 가격 데이터(`Device`)는 공시지원금 변동 등으로 수시로 변경됩니다. 만약 `Quote`에서 단순 Join이나 물리적 Foreign Key로 현재 가격을 참조하도록 설계했다면, 가격 갱신 시 과거 발행된 모든 견적서의 가격이 변조되는 치명적인 무결성 훼손이 발생했을 것입니다. 
하지만 현재 `Quote` 엔티티는 생성 시점의 `retailPrice`, `publicSubsidy`, `principal`을 **스냅샷(Snapshot)**으로 복사하여 저장합니다. 이는 견적 시스템의 본질인 **이력 불변성(Immutability)**을 지키는 가장 정석적이고 안전한 아키텍처입니다.

**[전자계약 연동을 위한 느슨한 결합(Loose Coupling)]**
생성된 견적 데이터가 내부 계약에 종속되지 않고 '전자계약 시퀀스'로 매끄럽게 넘어가도록, `Quote` 엔티티 내에 `contractId` 필드를 배치했습니다. 이는 물리적인 `@ManyToOne` 관계를 강제하지 않는 느슨한 참조(Soft Reference) 모델을 채택한 것으로, 추후 전자계약 시스템 모듈이 붙더라도 견적 데이터의 독립성을 유지한 채 유연하게 확장할 수 있는 준비된(Ready) 구조입니다.

**[인덱싱 및 성능 최적화]**
단말기 리스트 조회 속도를 극대화하기 위해 `Device` 테이블에 `(networkType, carrier, deviceName)`, `(networkType, carrier, modelName)` 등 클라이언트 쿼리 패턴에 정확히 일치하는 **복합 인덱스(Composite Index)**를 구축했습니다. 또한 최근 UUID(`@PrimaryGeneratedColumn('uuid')`)로 PK를 마이그레이션함으로써, 향후 분산 데이터베이스 환경이나 NoSQL 기반의 캐시 서버로 이전할 때에도 키 충돌 없이 즉각적인 스케일 아웃(Scale-out)이 가능해졌습니다.

## 3. 종합 평가 및 강점 (Strengths)

1. **메모리 연산을 통한 데이터베이스 부하 감소**
   할부원금(`principal`) 필드를 물리적 DB 컬럼으로 두어 중복 저장하지 않고, 조회 시점(`ConsultationsService`)에 백엔드 메모리 단에서 `Math.max(0, 출고가 - 공시지원금)`으로 실시간 계산하여 DTO로 매핑한 점은 훌륭합니다. 이는 스토리지 낭비를 줄이고, 불필요한 DB 쓰기/수정 I/O를 경감시키는 시니어 레벨의 설계입니다.
2. **보안 및 데이터 위변조 방지 (데이터 검증 로직)**
   견적 생성(`POST /api/consultations/quotes`) 시 클라이언트를 맹목적으로 신뢰하지 않고 오직 `device_id`만 받아온 뒤, 백엔드에서 다시 DB를 조회해 가격을 가져오며 `quote_name`과 `tag`마저 백엔드에서 자동 조합합니다. 클라이언트가 임의로 조작된 가격 페이로드를 POST하는 것을 원천 차단한 견고한 구조입니다.
3. **표준화된 예외 처리 (Error Handling)**
   단말기 조회 시 `404 NotFoundException`, 통신사/유무선 검증 불일치 시 `400 BadRequestException` 등 상황에 맞는 명확한 HTTP Status를 던짐으로써, 클라이언트와의 커뮤니케이션 비용을 줄였습니다.

## 4. 아쉬운 점 및 개선 과제 (Weaknesses & Action Items)

대규모 트래픽 발생 시 병목을 일으키거나, 다음 스텝(전자계약) 연동 시 충돌을 빚을 수 있는 잠재적 약점(Weaknesses)과 이에 대한 개선 방향입니다.

1. **동적 검색 쿼리의 B-Tree 인덱스 한계 (성능 병목)**
   - **문제:** 현재 `ConsultationsService`의 동적 검색 쿼리(`LIKE :keyword`, `%keyword%`)는 와일드카드가 문자열 앞부분에 존재하여, 기껏 만들어 둔 복합 인덱스를 타지 못하고 **풀 테이블 스캔(Full Table Scan)**을 유발합니다. 트래픽과 데이터가 누적되면 가장 먼저 병목 현상(CPU/Memory 스파이크)이 발생할 지점입니다.
   - **개선 제안:** 단순 `LIKE` 검색을 제거하고, PostgreSQL의 `tsvector` 기반 전문 검색(Full-Text Search) 인덱스를 도입하거나 Elasticsearch와 같은 검색 엔진으로 단말기 조회를 위임하는 아키텍처 리팩토링이 필요합니다.

2. **메모리 누수(OOM) 방지를 위한 Pagination 부재**
   - **문제:** `getDevices` 쿼리에서 `.getMany()`를 호출하여 일치하는 모든 데이터를 한 번에 서버 메모리로 로드하고 있습니다. 크롤링된 단말기가 방대할 경우 V8 엔진의 힙(Heap) 메모리 한계 초과가 발생할 수 있습니다.
   - **개선 제안:** Cursor 기반 페이지네이션(Cursor-based Pagination) 혹은 Offset/Limit 기반 페이지네이션을 DTO와 쿼리에 즉각 도입하여 데이터를 청크(Chunk) 단위로 분리해야 합니다.

3. **가격 변동에 따른 레이스 컨디션(Race Condition) 및 동시성 제어 부재**
   - **문제:** 사용자가 화면에서 A 단말기(출고가 100만 원)를 보고 견적 생성 버튼을 누르는 찰나의 순간, 크롤러 배치가 출고가를 110만 원으로 업데이트할 수 있습니다. 이 경우 사용자는 100만 원으로 인지하고 계약을 진행했지만, 백엔드 스냅샷은 110만 원으로 저장되어 409 Conflict 상황이 비즈니스적으로 발생합니다.
   - **개선 제안:** `Device` 엔티티에 TypeORM `@VersionColumn()`을 추가하여 **낙관적 락(Optimistic Lock)**을 구현해야 합니다. 또는 프론트엔드가 견적 생성 요청 시 자신이 화면에서 본 '기준 가격'을 함께 넘기도록 하여 서버의 현재 가격과 일치하지 않으면 예외를 던지고, 갱신된 가격을 다시 확인받게 하는 비즈니스 로직(409 상태 코드 반환) 추가가 필수적입니다.

4. **전자계약 연동을 위한 상태 머신(State Machine) 도입 필요**
   - **문제:** 현재 `Quote` 엔티티는 스냅샷을 훌륭하게 저장하지만, 견적서의 현재 상태(예: 임시저장 ➔ 고객검토중 ➔ 전자계약완료 ➔ 파기됨)를 추적하고 관리하는 필드가 없습니다.
   - **개선 제안:** 전자계약 모듈이 붙을 것을 대비하여 `QuoteStatus` Enum 컬럼을 추가하고, 전자계약 도메인에서 계약 체결 이벤트(Event)가 발생할 때마다 메시지 큐(RabbitMQ/Kafka) 또는 `EventEmitter`를 통해 견적 상태가 비동기적으로 업데이트되는 상태 머신 구조를 설계해야 합니다.
